# Trigger measurement — 2026-07-23

`tier: proven` — run on the `personal` machine, output pasted at the time.

## How it was measured (and why not with `run_eval.py`)

`skill-creator/run_eval.py` does not work for this skill: it creates a temporary command with
the `description` and measures whether *that* triggers. Because the real skill is installed
globally, it competes with the temporary one and the harness reports 0 on every query
(symptom: every positive at `rate=0/N`, only negatives pass).

Method used instead: run `claude -p "<query>" --model haiku` with `--output-format
stream-json`, drop the `system`/init event (where the skill name appears only because it is
available), and count a trigger when the skill is **selected** in the rest of the stream.

## Result

| | |
|---|---|
| Total | **12/13** |
| Positives that triggered | 7/8 |
| Negatives that did NOT trigger | **5/5** |
| Model | `haiku` (strictest test: if it triggers here, it triggers on Opus) |

The negatives are the strong data point: 5/5, including the near neighbour "Convertí este AVI a
MP4 manteniendo la calidad". The boundary is in the right place.

The one failure was noise: the most on-target query triggered 2 of 3 times when re-run with
the identical string. Sampling variance, not a gap in the `description`.

## Interference found: the session-objective rule

In `-p` mode, the global `CLAUDE.md` rule ("ask for the session objective before anything
else") fires before the skill. Claude often identified the skill correctly and then asked for
the objective instead of running it. That is why the measurement counts **selection**, not
execution. It affects any headless automation built on this config.
